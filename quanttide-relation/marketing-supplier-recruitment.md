# 招募企业主 IP 市场类供应商

## 业务意图

在小红书上问到一个博主，专做企业主 IP——帮一个老板把自己经营成行业里说得上话的人，靠内容攒信任，再把信任换成客户。看完我有两个反应。一是这事我们该做，二是我们缺的正是懂内容、懂流量的人。我们擅长软件，他们擅长把人变成一台获客机器，两样拼在一起，一门生意就成了。

念头落成一句需求：写一篇公告，公开找做企业主 IP 的市场类供应商——直接付费，或知识互换，我们出的是软件能力。

这句话派不出去。它由好几件事攒成，而且大部分决定在「写」之外：找什么样的供应商，对方缺什么，我们给什么，知识互换具体换什么，公告发在哪，谁接回应，接到之后怎么筛。每一条都会改公告写成什么样。把这些都留给「写」这个动作，上手的人（不管人还是 AI）只能拿模糊话把没定的地方糊过去，交一段四平八稳、谁也不得罪、也谁都说不动的东西。

这篇要做的就是把这句话拆到每一件都能单独派人做、做完有办法判。拆的时候盯三件事：派给谁，怎么算完，得等谁先做完。

## 哲学阐述

在拆之前先问一个更靠前的问题：这件事里到底有什么东西存在。

摊开看，真实存在的是三样。供应商——做企业主 IP 的市场类主体，有边界、能被指认。软件能力——我们握在手里的东西。接触——从我们伸到供应商那里的一次动作。公告归载体，它是接触的载体，全部意义在于被供应商读到、把人引过来。意向和回应归状态，「不知道我们」「收到公告」「愿意谈」说的是供应商处在哪一步，本身不占一样东西。对象、动作、载体、状态各归各位，后面写符号时一样不多、一样不少。

据此立下的判断是：这件事的单位是供应商这个对象和接触这个动作，一篇公告只是它们的中间载体。文案好不好，看它有没有把供应商从「不知道我们」带到「愿意谈」；离开这个动作去打磨文案，等于把载体当成了目的。

从同一条判断里还牵出两处。

一处是「一件」怎么算。一件事的边界落在它的完成能不能被判定：能判，它才是一件可以单独派出去的事；判不了，它只是连续性里的一个说法，交接出去也没人说得清交接了没有。这条是后面两步的地基——数学要有判据，代码要把判据写死，都从「能判才算一件」这里长出来。

另一处是人和智能体的位置。两者在任务面前是同一种东西的两个取值，都是执行者，差别只在一件事的判据能不能写成机械核对：写得成，归智能体；写不成，才归人。「哪些派给 AI、哪些留给人」因此不用另答，它是判据清晰度的推论。

## 数学实现

先看拆出来的单位长什么样。

一件事做下去，世界会变一点——盘上多一个文件、网上多一篇公告、手边多一份名单。把「世界此刻什么样」整体叫作状态，那么每件事就是把状态从一种样子换成另一种样子，是一个状态转移。

一个任务单元记四样东西：

```text
任务单元 ::= 名字
             执行者 : {智能体, 人}
             前置   : 状态上的条件
             后置   : 状态上的条件
             判据   : 可判定的完成条件
```

名字用来对账；前置是这件事允许开始的条件；后置是它做完之后状态必须满足的条件；判据是站在状态上算得出真假的式子。前置和后置是拆分者许下的愿，判据是把愿落成能验收的东西——一个任务单元只有判据可判定，才敢说「做完了」。

可判定在这里有具体含义。判据要么是程序能逐字核对的（文件在不在、含不含某段文字、一条命令退出码是不是零），要么是一个读得懂语境的智能体判个是或不是，要么只能由人拍板。这三种正好对上判据的三种取法：

```text
判据执行者 : {rule, agent, human}
```

`rule` 是程序机械核对，`agent` 是智能体判，`human` 是人拍板。一件事的判据能写成 `rule`，说明它已经拆得够硬，可以整个交给程序；只能写成一句要读懂才判得出的人话，才轮到智能体或人。步骤本身的执行者只有两种：

```text
步骤执行者 : {agent, human}
```

能交给智能体的都交给智能体，人只出现在两类位置：需要有人担后果的，和没有客观标准、只能拍的。

一条需求写成目标，落在最终想要的产物上：

```text
目标 G ≡ 存在一篇公告 d · d 写明了采购意向、直接付费与知识互换两种方式、我们提供软件
```

分解是拿出一组任务单元 T = {t₁, …, tₙ}，再给出先后关系 ≺，要满足三条：

```text
(1) 终态蕴含目标   post(t₁) ∧ … ∧ post(tₙ) ⇒ G
(2) 依赖保证前置   tᵢ ≺ tⱼ ⇒ post(tᵢ) ⇒ pre(tⱼ)
(3) 每个 tᵢ 的判据可判定
```

第一条说全部做完目标必然成立，没有哪一步白做，也没有哪一步做完目标还差一块。第二条说先后关系是有用的，前一步的后置恰好保证后一步允许开始。第三条是上面那条要求。

≺ 是个偏序——自反、反对称、传递。它允许两件事谁也不等谁，谁先做都行；不允许有环，甲等乙、乙等甲说明这个拆法自相矛盾，得回去把两件事并成一件，或换个切法。真实执行时，把偏序排成一条线（拓扑序）即可，线的差别只在互不依赖的任务换序。

拿公告这条需求走一遍。七个任务单元：

| 任务单元 | 执行者 | 前置 | 判据 |
|:--|:--|:--|:--|
| 定供应商画像 | human | 无 | 人拍板：供应商类型、对方缺什么、我们给什么，三样都写死 |
| 定交换方式 | human | 无 | 人拍板：付费与知识互换各写明边界 |
| 选渠道 | human | 无 | 人拍板：给出至少一个可发布的渠道 |
| 起草公告 | agent | 定供应商画像、定交换方式 | rule：草稿落盘且含「知识互换」；agent：通读像不像招募公告 |
| 发布公告 | human | 起草公告、选渠道 | 人拍板：公告已在选定渠道可见 |
| 收回应 | agent | 发布公告 | rule：回应清单落盘 |
| 初筛接触 | human | 收回应 | 人拍板：给出待接触名单 |

先后关系画出来是这样：

```text
定供应商画像 ┐
           ├─→ 起草公告 ┐
定交换方式 ┘             ├─→ 发布公告 ─→ 收回应 ─→ 初筛接触
选渠道   ───────────────┘
```

对着三条逐条看。终态蕴含目标：全部走完，手边有一篇发了的公告，写明了意向、两种方式和软件能力，G 成立。依赖保证前置：起草公告的前置要求画像与交换方式都已定，正好是它两个前置任务的后置；发布公告的前置要求草稿和渠道都在，也正好是它两个前置任务的后置；其余几条同构。判据可判定：四条 `rule` 判据能被程序核对，四条人拍板判据由人给出是或否，没有一条落空。

三样里最容易漏的是第二条。人写步骤习惯按时间排，排出来看着顺，但「发布」等了「起草」却没等「选渠道」，到了发布那天渠道还没定。偏序把这个漏洞摆到明面上：漏一条依赖边，图上就少一条箭头。

## 代码实现

上面七个任务单元，在本领域的格式里落成一份工作流定义：

```yaml
name: 找企业主IP市场类供应商
description: 写并发布一篇公告，招募做企业主 IP 的市场类供应商，接受直接付费或知识互换
steps:
- name: 定供应商画像
  description: 写清找什么样的供应商、对方缺什么、我们给什么
  executor: human
  criteria:
  - executor: human
    description: 画像三样写死，不留待定项
- name: 定交换方式
  description: 直接付费与知识互换两种方式各自写明边界
  executor: human
  criteria:
  - executor: human
    description: 两种方式的边界都已拍板
- name: 选渠道
  description: 定这篇公告发在哪里
  executor: human
  criteria:
  - executor: human
    description: 至少一个可发布的渠道已定
- name: 起草公告
  description: 按画像与交换方式写公告草稿，落在 artifacts/公告草稿.md
  executor: agent
  criteria:
  - executor: rule
    description: 草稿落盘
    path: artifacts/公告草稿.md
  - executor: rule
    description: 写明了知识互换
    file: artifacts/公告草稿.md
    contains: 知识互换
  - executor: agent
    description: 通读一遍，像不像一篇招募公告
- name: 发布公告
  description: 在选定的渠道上发布
  executor: human
  criteria:
  - executor: human
    description: 公告已在选定渠道可见
- name: 收回应
  description: 把各渠道的回应汇总成一份清单，落在 artifacts/回应清单.md
  executor: agent
  criteria:
  - executor: rule
    description: 回应清单落盘
    path: artifacts/回应清单.md
- name: 初筛接触
  description: 从清单里挑出值得先接触的对象
  executor: human
  criteria:
  - executor: human
    description: 待接触名单已定
```

字段和上面的四样一一对上：`name` 是名字，`executor` 是执行者，`criteria` 里每条判据写着谁判、怎么算完，`steps` 的排列顺序就是选定的那条拓扑序。前置和后置没有自己的字段，写在 `description` 里——这一段留给人和智能体读，程序核不了。

这段定义能做机械核对的部分，工具箱里已经实现。读它的是 `Workflow::from_value`：

```rust
use quanttide_work::workflow::Workflow;

let definition: serde_yaml::Value = serde_yaml::from_str(source)?;
let workflow = Workflow::from_value(&definition)?; // 读进来顺带校验语法
for step in workflow.steps() {
    println!(
        "{}：{}，判据 {} 条",
        step.name(),
        step.executor(),
        step.criteria().len()
    );
}
```

`from_value` 管的是字段合法性：步骤名不能空，`executor` 只能是 `agent` 或 `human`，判据只能取 `rule` / `agent` / `human` 三种、判法只能是 `path` / `absent` / `contains` / `run` 四种，出现不认识的字段当场报错。判据为空它不拦——一个单元一条判据都没有，语法上成立，但算不算「能算完」它不管，这条留给人。

三条分解条件里，程序替人看住的是取值的合法性；终态蕴含目标、依赖保证前置这两条没有对应字段，只能由拆的人拿着产物逐条读。机器能做的是在拆完之后把字段和取值扫一遍，让人省下核语法的力气。
