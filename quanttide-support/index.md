# 客户支持

## 概念

**工单**——客户提出来的一个问题，一次一条。它是问题侧：问题常年存在，工单是一次次被提出来的条目；一张工单关掉了，问题可能还在。

**工作日志**——一张工单的处理记录：问了什么、答了什么、依据是什么，交客户确认。它按本体系的范畴取名——工作日志记一次事件的现场，客服这边每张工单一份。它是客户确认的载体，也是将来提炼解决方案的唯一原料。

**解决方案**——从工作日志里提炼出来的解答，带适用条件。它是结果侧：跟问题走，不跟某一张工单走。同一个问题在不同客户环境下解法不同是常态，所以「什么条件下适用」是它的一部分，不是附注；产品改了、政策变了，旧版退位，取用只取在位的。

分工与两个现成的范畴一一对应，子系统不自建容器：**记录段**（工单 → 工作日志 → 客户确认）落 `journal` 范畴，按 `quanttide-support/<YYYY-MM-DD>.md` 收原始回答转成的日志，只增不改；**加工整理段**（日志 → 解决方案）落 `profile` 范畴，方案收在本目录，快照式只放最新一份，旧版自然退位。办完只看第一段，第二段早做晚做都不改变工单的死活。

三段范式照旧：第一段量潮自己需要客服所以做；第三段（服务模式标准化、售卖）排在前两段站住之后，现在不碰。

## 需求

量潮自己要做客服子系统，因为自己需要。现状是客户支持的提问散落在各个沟通渠道里，回答完就散，答的质量取决于当时谁在场，第二次遇到同类问题重答一遍。

这件事由四件事攒成：提问怎么落成工单；回答怎么落成工作日志并交客户确认；客户不回、超时、这事不该我们答这些结局怎么记；将来工作日志怎么提炼成带适用条件的解决方案。必须定的决策全在判定一侧——什么算工单、什么算日志、办完的判据、正常结局有哪几格；界面措辞、渠道对接只是文案与适配，边跑边改。

这些不定，系统就落不成实事：工单箱照建，回答照旧散在对话里，攒三个月还是零份工作日志。

## 意图

这件事里真实存在的是五样。工单——客户提的问题，一次一条。工作日志——一张工单的处理记录，一份对一份。客户确认——对一份日志的答复动作，一次一份。解决方案——从日志提炼的解答，带适用条件。适用条件——一条解决方案写明什么环境下成立，与方案一体。另有两个动作：取用（同类问题再进来时取在位的解决方案）与整合（人从确认过的日志里提炼方案）。

据此立下的核心断言是：**一张工单办完，不由「已回答」决定，由「有一份经客户确认的工作日志」决定**。问题解没解决是另一回事——超时、客户不回、不该我们答，都是工单的正常结局，记在日志里，不算失败。这条断言改动了后面的拆法：交付物从「回复」变成「一份要送出去确认的日志」，若按「答完即完」拆，系统只需要一个回复框，攒不下任何东西。

目标与不许踩破的两条：

```text
目标 G ≡ 每张办完的工单，有一份经客户确认的工作日志
inv1  被标为办完的工单 ⇒ 查得到那份经确认的日志
inv2  被取用的解决方案 ⇒ 带适用条件，且未退位
```

任务单元拆六条：

| 任务单元 | 执行者 | 前置 | 判据 |
|:--|:--|:--|:--|
| 定工单与工作日志的判定 | human | 无 | 人拍板：给定一条记录，当场判得出它是工单还是日志 |
| 定办完的判据 | human | 定工单与工作日志的判定 | 人拍板：办完 ⇔ 有经客户确认的日志；超时、不回、转出各记一格正常结局 |
| 提问落工单 | agent | 定工单与工作日志的判定 | rule：渠道里进来的提问落成工单，字段齐 |
| 回答落工作日志 | human | 定办完的判据 | 人拍板：每次回答产出一份日志并送客户确认，不是一句对话记录 |
| 定提炼的入口 | human | 回答落工作日志 | 人拍板：从确认过的日志里选料提炼解决方案，方案带适用条件，落本目录快照替换 |
| 核回溯 | agent | 回答落工作日志 | rule：每张办完的工单查得到确认过的日志，缺的退回 |

六条里最容易整个被忘掉的是「定提炼的入口」：第一段跑起来日志天天在长，第二段既没有界面也没有期限，一拖再拖；拖的时候系统看着一切正常。

规格、实现两个阶段待补：规格要把判定与字段落成语言无关的定义，字段对着真实的工单与日志核；实现要落成可执行形态。
