# 客户支持

## 概念

**工单**——客户提出来的一个问题，一次一条，带着提出它的上下文。它是问题侧：问题常年存在，工单是一次次被提出来的条目，一条工单办完了，问题可能还在。

**解决方案**——回答沉淀成的解答，下一次遇到同类问题直接取用。它是结果侧：不跟某一张工单走，跟问题走。答复不是解决方案——答完就散的是一次性消耗，攒不下来；能被取用的才算。

**服务模式**——同一类问题的解决方案攒到一定完整度，能说明这类业务怎么运转。它是第三段的东西，现在不碰，只在这里占个位。

工单与解决方案的这对分离不是新发明：议事域里议题与决议是同一副骨架，问题侧与结果侧分开，办完的条目落成可查的身份。我们所有系统走同一条三段路——从自己出发，找到这个领域从碎片到系统的演化规律，再推己及人。客服的第一段是量潮自己需要客服，第三段（服务模式标准化、售卖）排在两件东西站住之后。

中间那段演化规律，日志里已经写过一次：碎片是散在各处的一问一答，系统是一套可取用的解决方案，把两者连起来的是人的整合。它不自动发生，也不打算自动化——它就是被安排的工作。

## 需求

量潮自己要做客服子系统，因为自己需要。现状是客户支持的提问散落在各个沟通渠道里，回答完就散，第二次遇到同类问题重答一遍，答的质量还取决于当时谁在场。

这件事由四件事攒成：提问怎么落成工单；回答怎么落成解决方案；第二张同类工单进来时，解决方案怎么被找到；一张工单什么时候算办完。必须定的决策全在判定一侧——什么算一个工单、什么算一个解决方案、办完的判据写成什么；界面措辞、渠道对接只是文案与适配，可以边跑边改。

这些不定，系统就落不成实事：工单箱照建，回答照旧是一次性消耗，攒三个月还是零个解决方案。

## 意图

这件事里真实存在的是四样。工单——客户提的问题，一次一条。解决方案——沉淀下来的解答，可被取用。取用——第二张同类工单进来时用上已有解决方案的动作。整合——把零散解答归拢成一个可取用的解决方案的动作，执行者是人。

据此立下的核心断言是：**一张工单办完，不由「已回答」决定，由「它挂上了一个可取用的解决方案」决定**。这条断言直接改动了后面的拆法——回答动作不再是终点，落成解决方案才是；如果按「答完即完」拆，系统只需要一个回复框，攒不下任何东西。

目标与不许踩破的两条：

```text
目标 G ≡ 每张工单办完时，挂得上一个可取用的解决方案
inv1  被标为办完的工单 ⇒ 查得到它挂的解决方案
inv2  解决方案只增不丢：被取用之后修正出新版本，旧版本仍在
```

任务单元拆五条：

| 任务单元 | 执行者 | 前置 | 判据 |
|:--|:--|:--|:--|
| 定工单与解决方案的判定 | human | 无 | 人拍板：给定一条记录，当场判得出它是工单还是解决方案 |
| 定办完的判据 | human | 定工单与解决方案的判定 | 人拍板：办完 ⇔ 挂上可取用的解决方案，写成可判定断言 |
| 提问落工单 | agent | 定工单与解决方案的判定 | rule：渠道里进来的提问落成工单，字段齐 |
| 回答落解决方案 | human | 定办完的判据 | 人拍板：每次回答产出可取用的解答文本，不是一句对话记录 |
| 核回溯 | agent | 回答落解决方案 | rule：每张标为办完的工单查得到它挂的解决方案，缺的退回 |

五条里最容易整个被忘掉的是「回答落解决方案」——工单箱、渠道对接都是看得见的工程，落解决方案这一步没有界面，忙起来最先被砍，砍掉之后 G 永远成立不了。

规格、实现两个阶段待补：规格要把上面的判定与字段落成语言无关的定义（对着 `data/journal/quanttide-support/` 的真实问答核字段），实现要落成可执行形态。
