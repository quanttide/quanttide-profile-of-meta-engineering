# 议事与决议

## 概念

五个程序名词先给定义，再谈需求。

**议事规则**——一个议事机构的自有法：谁能动议、发言按什么顺序、怎么修正、几票算过、什么算程序问题什么算实质问题。它先于任何一次会议存在，规定「怎么吵、怎么修、怎么表决」，不规定「吵什么」；规则换一套，议题还是那个议题。

**议程**——一次会议要处理的事项清单，有序。议程与议题是容器与条目：会前先定临时议程再逐项批准，顺序本身就是权力，排在后面的等于没议；同样的议题，排法不同是两份议程。

**议题**——议程上的一个条目，有编号、有摘要，指向要讨论或决定的那件事。它是容器层：问题（issue）常年存在，议题是一次次被排上桌面的条目，议题办完了，问题还在；一条议题在讨论中只归一个机构的议程，可被交换。

**草案**——动议落成的文字载体，挂在一条议题下，带提案国与版本链。两条铁律来自安理会：不在议程上的议题，其草案不进审议；草案可改、可撤、可重提，它不是决定。

**决议**——草案经一次表决通过后拿到的编号身份：发号、文本冻结、进档案。相变发生在表决那一瞬，通过之前叫草案，通过之后是决议；没通过的仍是草案，改了版本可以再提。

机构侧。**议事机构**是有权按议事规则集体做决定的合议体，三个要件：有成员、有法定人数、开会走规则——公司代表大会、联盟代表大会、实训基地代表大会都是。**成员与代表**：成员是有席位和表决权的主体，代表是成员的产生方式，由单位派出。**法定人数**是能做出有效决定的最低出席数：不到法定人数，会可以开，决定不能做。**主席**主持会议、裁定程序问题与发言顺序，管程序不管内容。**表决权与特别表决权**：一席一票是常态，特别表决权是某些成员的票有超额效力——安理会五常的否决权是原型，我们的「创始人认证」属于这一类：它不是第 n 票，是挂在结果上的独立闸门。

归属关系：规则与议程属于机构——机构成立先有规则，议程属于机构的一次会议；跨机构交换议题是把条目挂到对方议程上，草案与决议不随议题走，草案跟提案国，决议跟通过它的机构。

落成类型是五样：Assembly、Member、AgendaItem、Draft、Resolution——Assembly 有议程，议程收 AgendaItem，AgendaItem 下挂 Draft，Draft 经表决升成 Resolution。

## 需求

内部协作现在是三段串行：沟通发邮件，团队整理提案进议事环节，通过以后再走新媒体发布。流程不短，而核心只有议事——把沟通与发布也压进议事流程里，发布就成了议事的正式产物，不必单走一段。

跨机构一侧，联盟代表大会要协调公司代表大会和实训基地代表大会，三个代表大会之间要交换议题——议题怎么在三者之间流动，是这套流程里最大的难题。

还有决议名分的问题：按定义联盟是社区的治理机构，但联盟决议不能完全等同于社区决议，中间缺一个定义。早期先用强约束：经创始人认证的公司、联盟或者实训基地的决议，才能变成社区决议，发在量潮议事中心的官网上。

这句话派不出去。它由四件事攒成：议事收编沟通与发布的边界划在哪、三个代表大会之间议题交换的规则、「社区决议」拿什么条件判定、认证这个动作挂在流程哪一步。真正必须定的决策全在判定与规则一侧：判定条件写成什么断言、交换谁发起谁接收、认证放在哪一步之后；邮件怎么写、发布文案怎么措辞只是文案。这些不定，「收进议事流程」就落不成实事：流程照画，决议照旧分不清名分。

拆的时候盯三件事：派给谁，怎么算完，得等谁先做完。

## 意图

拆之前先问：这件事里到底有什么东西存在。

摊开看，真实存在的是七样。草案——挂在议题下的文本，带提案国与版本，表决前随时会变。决议——草案表决通过后拿到的身份，发号即冻结，只剩认证与发布两格相位。代表大会——三个实例：公司、联盟、实训基地各一个，议题在它们之间流动。机构——公司、联盟、实训基地、社区，决议由前三种产生。议题——要跨代表大会交换的东西。认证——创始人对一条决议的背书动作，一次一个决议。议事与发布——表决草案与决议上官网的两个动作；压缩后发布挂在议事之后，不再并列。邮件是沟通的载体，收编之后不占一个环节。

据此立下的判断是：一条决议的效力不由机构名分决定，由「通过 + 创始人认证」两个可查的动作决定；议事是决议走向发布的唯一通道，发布是它的后置，不是串行的下一段。按这条判断，「联盟决议是不是社区决议」不用再争名分，代入判定条件当场判得出真假；三代表大会的议题交换只需一条规则，不需名分协调——后面的拆法因此只有一处定义、一处挂接，没有「协调名分」这类任务。

归位之后，把拆法写成可判定的式子。先看议题、草案与决议三样长什么样：

```text
AgendaItem ::= id       : ItemId              # 议题编号
               summary  : Str
               onAgenda : Bool                 # 是否已上议程

Draft ::= item     : ItemId                    # 只挂一条议题
          text     : Version                   # 每次修订出一个新版本
          sponsors : Set[Member]               # 提案国，可增可撤
          state    : {submitted, onTable, passed, rejected}

Resolution ::= id    : ResId                   # 表决通过才发号，一号一命
               item  : ItemId
               org   : {Company, Alliance, TrainingBase}
               phase : {pending, certified, published}

C(r) ≡ phase = certified ∨ phase = published   # 社区决议的早期判定条件（能成为决议，通过是前提）
```

四个动作各有前置与后置：

```text
review     : pre  草案的议题在议程上 ∧ sponsors ≠ ∅   # 不在议程上，草案不进审议
             post state = onTable
deliberate : pre  state = onTable
             post 通过 ⇒ state = passed，发号产生决议（phase = pending）
                    否决 ⇒ state = rejected，改版本可重提
certify    : pre  存在决议 r ∧ org ∈ {Company, Alliance, TrainingBase}
             post r.phase = certified
publish    : pre  C(r)                  # 官网只收满足 C 的决议
             post r.phase = published
```

一条需求写成目标，落在最终想要的产物上：

```text
目标 G ≡ ① 判定条件 C 写死，任给一条决议当场判得出真假
         ② 议事收编沟通与发布，发布只在 deliberate 与 certify 之后
         ③ 三个代表大会之间，议题交换各有一条写死的规则
```

不许被踩破的三条：

```text
inv1  被称为社区决议 ⇒ C(r)          # 未通过或未认证的，成不了社区决议
inv2  发在议事中心官网 ⇒ certified(r)
inv3  审议中的草案 ⇒ 其议题在议程上   # 先上牌桌，再碰草案
```

这套式子的 Lean 形式见同目录 `index.lean`：论域、三个类型、四个动作的前置后置与三条不变量写成定义与定理。

分解是拿出一组任务单元 T = {t₁, …, tₙ}，再给出先后关系 ≺，要满足三条：

```text
(1) 终态蕴含目标   post(t₁) ∧ … ∧ post(tₙ) ⇒ G
(2) 依赖保证前置   tᵢ ≺ tⱼ ⇒ post(tᵢ) ⇒ pre(tⱼ)
(3) 每个 tᵢ 的判据可判定
```

拿「把这套议事与决议的规矩立起来」走一遍。六个任务单元：

| 任务单元 | 执行者 | 前置 | 判据 |
|:--|:--|:--|:--|
| 定社区决议判定条件 | human | 无 | 人拍板：C 写成可判定断言，给定一条决议当场判得出真假 |
| 定议事收编边界 | human | 定社区决议判定条件 | 人拍板：流程只剩提案→议事→发布一段，发布前置引用 C |
| 定议题交换规则 | human | 无 | 人拍板：三个代表大会两两之间，谁发起、谁接收、何时排期各有唯一规定 |
| 认证动作入流程 | human | 定社区决议判定条件、定议事收编边界 | 人拍板：认证是议事通过后的一步，认证记录与决议一一对应 |
| 官网发布挂接 | agent | 定议事收编边界、认证动作入流程 | rule：发布接口拒绝不满足 C 的决议 |
| 核回溯 | agent | 认证动作入流程、官网发布挂接 | rule：每条已发布的社区决议查得到通过记录与认证记录，缺一退回 |

先后关系画出来是这样：

```text
定社区决议判定条件 ──→ 定议事收编边界 ──→ 认证动作入流程 ──→ 官网发布挂接 ──→ 核回溯
        │
        └──→ 定议题交换规则（独立，不进这条链）
```

对着三条逐条看。终态蕴含目标：六个走完，C 立下了、流程收成一段且发布引用 C、交换规则写死，G 的三条全成立。依赖保证前置：收编边界等的是 C 立下，认证动作等的两件（C、边界）分别来自它的两个前置任务，发布挂接与核回溯的前置同样对得上。判据可判定：三条人拍板判据由人给是或否，两条 rule 判据程序核得了，一条 agent 判据逐条过。

三样里最容易漏的是独立的那条。链上的五步排得再顺，「定议题交换规则」不进链，忙着走判定、认证、发布的时候它一步没动，三个代表大会之间照样交换不了议题——偏序里谁也不等谁的那一步，最容易整个被忘掉。

核心断言确实改动了后面的拆法：效力由两个动作决定，所以判定只有一处 C、官网挂接只查 C，没有「给联盟决议和社区决议各立一个定义」的两处任务；若按名分拆，判定要写两套、发布要处处查名分，链会多出至少两步，而且查不过来。

## 规格

工作流定义成一句话：「提案 → 议事 → 认证 → 发布」四步，前两步长在草案上——草案表决通过才产生决议，后两步长在决议上；每步各有前置，发布这一步的前置就是判定条件 C(r)。

数据模型分两截：草案侧四个字段——议题编号、版本、提案国、相位（提交、上桌、通过、否决四格）；决议侧四个字段——决议号、议题编号、机构（只能是公司、联盟、实训基地三者之一）、相位（待认证、已认证、已发布三格）。三条不变量落成字段约束：标为社区决议的，相位必须已越过认证；相位是已发布的，认证必然在场；上桌的草案，其议题必在议程上。同目录的 `index.cue` 就是这份定义的 schema 形态，一份写死，供多种语言的实现共同引用。

字段对着仓库真值核：机构取值对的是公司、联盟、实训基地三个主体名录；相位与认证记录对的是议事中心的决议记录，一条决议一条相位、一条认证记录。程序管得住的：取值合法性、相位转移的前置、发布闸门（不满足 C 的记录进不了已发布）、回溯查询（每条已发布决议查得到通过与认证两条记录）。只能人核的：判定条件 C 是否仍代表意图——条件是人立的，立错了程序照错的判；创始人认证的真伪；三代表大会议题交换的规则是否合理（规则未定，还压在意图的任务单元里）。

## 实现

`index.py` 是落成 Python 的可执行形态：每个动作各自带前置检查，前置不满足当场报错，发布入口只放行满足 C(r) 的决议——inv2 那道闸门就设在 `publish` 里；机构取值写死成一个白名单，对着主体名录验。

验收走字段合法性检查：相位取值与转移、机构白名单、发布前置逐项查得过。程序管不住的部分写明由谁兑：认证的真伪由创始人本人兑，判定条件的解释与更新由人兑，议题交换规则的落地由联盟代表大会兑。
