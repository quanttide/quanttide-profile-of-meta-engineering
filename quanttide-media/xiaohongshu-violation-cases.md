# 建立小红书违规判例库

## 业务意图

我们手上不止一个小红书账号。号一多，违规就不再是哪一个人、哪一个号的事：限流、删帖、禁言、扣分，各号各犯，事后各忘。同一条坑，甲号踩过，乙号过两周原样再踩一遍。这些事散在本人的记忆、聊天记录和平台通知里，谁都说不清一共出过多少、都是什么原因、后来改没改。

念头落成一句需求：建一个小红书违规判例库，把违规问题透明化。

这句话派不出去。它由好几件事攒成，而且大部分决定在「建库」之外：什么算一条判例，一条要记哪几样，记在哪，谁来记，什么时候记，记完谁核，核完谁能看、能看到什么程度。这些不定，「建库」就只能建成一个目录加几段话，谁也说不清完工没有。

这篇要做的就是把这句话拆到每一件都能单独派人做、做完有办法判。拆的时候盯三件事：派给谁，怎么算完，得等谁先做完。

「透明化」也得先落成一句能验的话。它不是「有一份材料」，而是：每一件已知的违规，都有一条能被找到、能读懂的记录。找得到、读得懂，才叫透明；拿一份总结代替，等于把没做的部分藏了起来。

## 哲学阐述

拆之前先问：这件事里到底有什么东西存在。

摊开看，真实存在的是四样。账号——平台上一个可被处置的主体，有边界、能被指认。违规——平台对某个账号的一次处置，有时间和指向；它是**发生**，发生过一次就是一次，不随账号后来是否恢复而消失。平台规则——平台援引的那条规则，是一段外部给定的文本。判例——一次违规的记录，是载体。库——判例的集合，也是载体。账号此刻是正常还是限流中，说的是**状态**，状态本身不占一样东西。

据此立下的判断是：这件事的单位是「一次违规」这个发生，判例是它的记录，库是记录的集合。透明不是把库做得多整齐，而是每一件已知的违规都有一条能被找到、能被读懂的记录。离开这个判断去打磨库的目录、分类和封面，等于把载体当成了目的。

由同一条判断还牵出三处。

一处是判例与规则的分工。平台规则是「应当怎样」，一次违规是「实际怎样被判过」。库收的是后者——收事实，不收规则摘抄。混进来一批规则文本，翻库的人就分不清哪条是我们真踩过的、哪条只是抄来的，透明反倒被稀释。

一处是「一条」怎么算。一件事的边界落在它的完成能不能被判定：一条判例能被核对是不是记录完整，缺了触发内容或缺了平台裁定，它就不算一条；能判，才敢说这条立住了。这条是后面两步的地基。

一处是人和智能体的位置。两者在任务面前都是执行者，差别只在一件事的判据能不能写成机械核对：能从平台通知、后台截图里逐字抄下来的字段，归智能体；「这条到底为什么被判」要读懂语境的，也归智能体判；「要不要对外公开、公开到什么程度」担的是后果，只能人拍板。

## 数学实现

先看拆出来的单位长什么样。

一件事做下去，世界会变一点——盘上多一个文件、清单上多一条记录、库里多一个入口。把「世界此刻什么样」整体叫作状态，那么每件事就是把状态从一种样子换成另一种样子，是一个状态转移。

一个任务单元记四样东西：

```text
任务单元 ::= 名字
             执行者 : {智能体, 人}
             前置   : 状态上的条件
             后置   : 状态上的条件
             判据   : 可判定的完成条件
```

名字用来对账；前置是这件事允许开始的条件；后置是它做完之后状态必须满足的条件；判据是站在状态上算得出真假的式子。前置和后置是拆分者许下的愿，判据是把愿落成能验收的东西——一个任务单元只有判据可判定，才敢说「做完了」。

判据的取法沿用前几篇：`rule` 是程序机械核对，`agent` 是智能体判，`human` 是人拍板；步骤本身的执行者只有 `agent` 与 `human` 两种。

一条需求写成目标，落在最终想要的产物上：

```text
目标 G ≡ 存在一组判例记录 C，使每个已知违规 v 都对应 C 中一条记录，
         该记录写明触发内容、平台裁定与处理状态，且在库入口里能被查到
```

分解是拿出一组任务单元 T = {t₁, …, tₙ}，再给出先后关系 ≺，要满足三条：

```text
(1) 终态蕴含目标   post(t₁) ∧ … ∧ post(tₙ) ⇒ G
(2) 依赖保证前置   tᵢ ≺ tⱼ ⇒ post(tᵢ) ⇒ pre(tⱼ)
(3) 每个 tᵢ 的判据可判定
```

≺ 是个偏序，允许两件事谁也不等谁，不允许有环。

拿这条需求走一遍。八个任务单元：

| 任务单元 | 执行者 | 前置 | 判据 |
|:--|:--|:--|:--|
| 定收录口径 | human | 无 | 人拍板：什么算一条、哪些账号纳入，两样都写死 |
| 定字段清单 | human | 无 | 人拍板：每条记哪几样、每样怎么填，都写死 |
| 定存放位置 | human | 无 | 人拍板：库落在哪个路径 |
| 收集历史违规 | agent | 定收录口径 | rule：原始清单落盘；agent：逐条指得回一次真实处置 |
| 逐条立判例 | agent | 定字段清单、收集历史违规 | rule：判例目录落盘；agent：每条字段齐全、指得回原始清单 |
| 核判例完整 | agent | 逐条立判例 | agent：逐条过字段，缺项已退回 |
| 定公开边界 | human | 逐条立判例 | 人拍板：每条判例都标了公开或内部 |
| 汇总入库 | agent | 核判例完整、定存放位置、定公开边界 | rule：库入口落盘且出现「平台裁定」；agent：入口列全每条判例 |

先后关系画出来是这样：

```text
定收录口径 ─→ 收集历史违规 ┐
定字段清单 ──────────────┼─→ 逐条立判例 ─┬─→ 核判例完整 ──┐
                          ┘                │                ├─→ 汇总入库
                                           └─→ 定公开边界 ───┘
定存放位置 ─────────────────────────────────────────────────┘
```

对着三条逐条看。终态蕴含目标：全部走完，每条已知违规都有一条记录，字段齐、公开边界标了、库入口能查到，G 成立。依赖保证前置：逐条立判例的前置要求字段清单与原始清单都在，正好是它两个前置任务的后置；汇总入库的前置要求判例核过、位置定了、公开边界标了，也正好是它三个前置任务的后置；其余几条同构。判据可判定：两条 `rule` 判据程序核得了，四条 `agent` 判据由智能体逐条过，两条人拍板判据由人给是或否。

三样里最容易漏的是第二条。人写步骤习惯按时间排，排出来看着顺，但「逐条立判例」等了「收集历史违规」却没等「定字段清单」，判例就会边立边改字段，早立的和晚立的对不齐。偏序把这个漏洞摆到明面上：漏一条依赖边，图上就少一条箭头。

## 代码实现

上面八个任务单元，在本领域的格式里落成一份工作流定义：

```yaml
name: 建立小红书违规判例库
description: 把手上多个小红书账号遇到过的违规逐条录成可查的判例，落在仓库里
steps:
- name: 定收录口径
  description: 写清什么算一条判例、哪些账号纳入
  executor: human
  criteria:
  - executor: human
    description: 口径写死，不留待定项
- name: 定字段清单
  description: 写清每条判例记哪几样、每样怎么填
  executor: human
  criteria:
  - executor: human
    description: 字段与填法都已拍板
- name: 定存放位置
  description: 定判例记在哪个路径
  executor: human
  criteria:
  - executor: human
    description: 存放位置已定
- name: 收集历史违规
  description: 从各账号后台、平台通知、聊天记录里翻出历史违规，落在 artifacts/违规原始清单.md
  executor: agent
  criteria:
  - executor: rule
    description: 原始清单落盘
    path: artifacts/违规原始清单.md
  - executor: agent
    description: 清单逐条指得回一次真实处置
- name: 逐条立判例
  description: 按字段清单，为原始清单里每条违规写一条判例，落在 artifacts/判例/ 下
  executor: agent
  criteria:
  - executor: rule
    description: 判例目录落盘
    path: artifacts/判例/
  - executor: agent
    description: 每条判例字段齐全，能指回原始清单里的一条
- name: 核判例完整
  description: 逐条核对字段与证据，缺项的退回补
  executor: agent
  criteria:
  - executor: agent
    description: 每条判例字段齐全，缺项已退回
- name: 定公开边界
  description: 逐条定这条判例对外可见还是一律内部
  executor: human
  criteria:
  - executor: human
    description: 每条判例都标了公开或内部
- name: 汇总入库
  description: 生成库入口 artifacts/判例库.md，列出全部判例
  executor: agent
  criteria:
  - executor: rule
    description: 库入口落盘
    path: artifacts/判例库.md
  - executor: rule
    description: 入口里出现「平台裁定」一栏
    file: artifacts/判例库.md
    contains: 平台裁定
  - executor: agent
    description: 入口列全每条判例，逐条指得到判例文件
```

字段和上面的四样一一对上：`name` 是名字，`executor` 是执行者，`criteria` 里每条判据写着谁判、怎么算完，`steps` 的排列顺序就是选定的那条拓扑序。前置和后置没有自己的字段，写在 `description` 里——这一段留给人和智能体读，程序核不了。

这段定义能做机械核对的部分，工具箱里已经实现，读它的是 `Workflow::from_value`：

```rust
use quanttide_work::workflow::Workflow;

let definition: serde_yaml::Value = serde_yaml::from_str(source)?;
let workflow = Workflow::from_value(&definition)?; // 读进来顺带校验语法
for step in workflow.steps() {
    println!(
        "{}：{}，判据 {} 条",
        step.name(),
        step.executor(),
        step.criteria().len()
    );
}
```

`from_value` 管的是字段合法性：步骤名不能空，`executor` 只能是 `agent` 或 `human`，判据只能取 `rule` / `agent` / `human` 三种、判法只能是 `path` / `absent` / `contains` / `run` 四种，出现不认识的字段当场报错。判据为空它不拦——一个单元一条判据都没有，语法上成立，但算不算「能算完」它不管。

对照真值，这份定义里有两点是程序管不住的，只能由人核。一是「每条判例」的**每**：`path: artifacts/判例/` 只核目录在不在，目录里该有几条、有没有漏，程序不知道；入口里 `contains: 平台裁定` 也只证明这一栏出现过一次，证不了每条都在。这两条都记在 `agent` 判据里，靠通读兜。二是判例与规则的分工：库该收事实、不该收规则摘抄，这条判断没有任何字段对应，程序扫不出来，只能由拆的人拿着成品逐条读。

三条分解条件里，程序替人看住的是取值的合法性；终态蕴含目标、依赖保证前置这两条没有对应字段，只能由拆的人拿着产物逐条读。机器能做的是在拆完之后把字段和取值扫一遍，让人省下核语法的力气。
