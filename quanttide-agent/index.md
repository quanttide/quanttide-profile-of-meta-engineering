# 智能体：元认知档案（quanttide-agent 域）

**一句话目标待创始人给定**——不外推、不代配。可陈述的现状：量潮的日常工作由智能体承担，session 数据是副产品；三处存储——pi（`~/.pi/agent/sessions`，337 段，按工作目录分 89 个项目目录，JSONL）、opencode（81 个文件）、hermes（体量另核）；提炼物体系已在 `quanttide-profile-of-agent-engineering` 仓运行（循环范式、技能、提示词、智能体配置，按业务域组织）。

## 核心循环

**session → 落档（第一段）；落档日志 → 提炼物（第二段）。**与客户支持同构：session 之于本域 ≈ 工单之于客服——一次次发生、原始、事件侧；提炼物 ≈ 解决方案——跟场景走，不跟某一段 session 走。

- **session**——一段智能体会话，原始记录（工作目录、模型、往来消息）。原料，不是资产。
- **落档**——把一段 session 写成记录，落日志仓。第一段的产物。
- **提炼物**——从落档日志里提出来的东西：循环范式、技能、提示词、智能体配置。第二段的产物，住 profile 仓（现状组织：`default/` + 各业务域/，域下 `loops`、`skills`、`prompts`、`agents`、`sessions`、`contexts`）。

## 待定判据（岔路问答未做，不得先填）

1. **办完的判据**：客服是「有一份经客户确认的工作日志」；session 没有客户，对应的收口判据是什么，待定；
2. **选料判据**：337 段 session 不是每段都值得提炼，哪一段值得进第二段，待定；
3. **四格结局**：客服的四格（已确认/超时/不回/转出）在本域的对应，待定。

## 两段分工与落位

第一段（原始 session → 落档记录）落 `journal` 范畴，只增不改，细节见 `journal.md`；第二段（落档日志 → 提炼物）落 `profile` 范畴，快照替换、旧版退位，细节见 `profile.md`；对外口径落 `brochure`，细节见 `brochure.md`。子系统不自建容器，存储、版本、正本、判据都借范畴。

## 设计范式三段

第一段自己需要才做：量潮自己用智能体干活，session 是自己的副产品，先自用。第二段找演化规律：session → 落档 → 提炼物，与客服的工单 → 工作日志 → 解决方案同骨架。第三段推己及人：售卖口径现在不写，占位。

## 任务单元

| 任务 | 执行者 | 判据 |
|:--|:--|:--|
| 定 session、落档、提炼物的判定 | human | 给定一段记录，当场判得出它处在哪一段 |
| 定办完的判据 | human | 上面三条待定判据一条条落死 |
| session 落档 | agent | 按工作目录落对应域的日志，字段齐 |
| 提炼物的选料 | human | 只从落档日志里选，选出来的东西带适用场景 |
| 核回溯 | agent | 每份提炼物指得到它的来源日志 |

## 已有资产（别重复建设）

- `quanttide-profile-of-agent-engineering` 仓：循环范式、技能、提示词、智能体配置的现成组织与维护规范（以实际配置为准、cp 即用、不重复维护可安装内容）——本档案不推翻它，只在它上面补两段分工与判据；
- `quanttide-meta/data/profile/quanttide-agent/pi-to-hermes.md`：已有的需求/意图档案；
- session 原文在各 harness 的存储里，落档日志只写记录与指针，不留副本。

## 边界

- 本域的提炼物是领域资产，不与 `~/.pi`、`~/.hermes` 等机器上的工作配置混——机器配置是采集源，仓是正本；
- 范畴不补领域判断：三条待定判据必须人给，填错了落位再对也枉然。
