# 把三个记忆集的认知地图本体移交元工程

## 业务意图

创始人的记忆仓里有三个集：default（创业与个人主线）、fiction（写作主线）、work（工作主线）。每个集各有一份 profile 档案，档案是散文写的；每个集又各有一份由档案转出来的 `index.ttl`，把散文里的条目变成了认知地图上的节点和有向边。

三份 TTL 摆在一起看，它们描述的是同一件事的三个取值：一个人被什么触发、手上有什么办法、这些办法最终服务于什么。default 和 work 用同一套类名（触发点 / 情绪 / 方法 / 价值 / 排除的形态），fiction 换成创作语境的三轴（创作困境 / 创作方法 / 创作动机）。同一副骨架，三个名字不同的版本。

念头落成一句需求：把这套骨架从创始人私仓里搬到元工程领域去加工——在本体该被定义、被比较、被收进规范的地方继续做，而不是留在三个集里各写各的。

这句话派不出去。它由好几件事攒成，而且大部分决定不在「搬」这个动作里：本体到底以什么为单位（是类与态射，还是一堆具体条目）、三份之间的共性和差异怎么摆、搬过去之后跟元工程已经写下的本体定义对不对得上、搬到什么程度算搬完。每一条都会改交付物长什么样。把这些都留给「搬」，上手的人（不管人还是 AI）只能拿模糊话把没定的地方糊过去，交一份看着像本体、其实没交代清楚的东西。

这篇要做的就是把这句话拆到每一件都能单独派人做、做完有办法判。拆的时候盯三件事：派给谁，怎么算完，得等谁先做完。

## 哲学阐述

在拆之前先问一个更靠前的问题：这件事里到底有什么东西存在。

摊开三份 TTL 看，真实存在的是四样。

认知地图上的节点是**对象**。它们的类不多：default 与 work 是触发点、情绪、方法、表达、价值、排除的形态；fiction 是创作困境、创作方法、创作动机。类名不同，位置相同——都是「情境」「办法」「归宿」这几格。

连接节点的是**动作**。四条有向关系：触发（触发点 → 情绪）、应对（情境 → 方法，情境可以是触发点也可以是情绪）、服务于（方法 → 价值或动机）、排除（价值 → 被排除的形态）。这四条在任何一本小说、任何一个工作场景里都成立，跟具体是谁的故事无关。

承载它们的**载体**有两层。一层是散文档案（`profile/*.md`），一层是 TTL（`index.ttl`）——后者是前者的转换产物，每个集一份，各有自己的命名空间。本体当前住在 TTL 里，但 TTL 里同时住着别的东西：每一条具体条目也是 TTL 里的一个节点。这是本体和实例挤在同一个载体里的状态。

最后是**状态**。条目处在哪种归属状态：属于哪个集、出自哪份档案（`pf:file`）、是独立成节还是只在句子里出现过（`pf:quote`）。这些说的是实例的状态，不是骨架的状态。

据此立下的核心断言是：**三个集共用同一副本体骨架——情境 → 方法 → 归宿**。四条态射的语义处处不变，变的只是类的名字随集的主题替换。所以三份 TTL 不是三套本体，是**一套本体的三个实例**。

从这条断言里直接牵出这次移交的单位：**搬的只能是本体（类、态射、对象属性），不是条目**。条目是实例，它跟着各自的集和各自的日志才有意义，留在私仓；骨架才是能在别处被重新定义和比较的东西，它进元工程。

这条也改动了后面的拆法。既然单位是本体，数学那步的任务里就没有「把 N 条条目搬过去」这件事，只剩下定边界、抽共性差异、对齐口径、核可搬运，一条搬条目的都没有。单位选错，后面每一步都会围着实例打转，最后交出一份 TTL 的副本而不是本体。

## 数学实现

先看拆出来的单位长什么样。

一件事做下去，世界会变一点——元工程仓里多一个文件、多一张对照表、对本体的一段定义多一条能被引用的表述。把「世界此刻什么样」整体叫作状态，那么每件事就是把状态从一种样子换成另一种样子，是一个状态转移。

一个任务单元记四样东西：

```text
任务单元 ::= 名字
             执行者 : {智能体, 人}
             前置   : 状态上的条件
             后置   : 状态上的条件
             判据   : 可判定的完成条件
```

一条需求写成目标，落在最终想要的产物上：

```text
目标 G ≡ 元工程仓里存在一份本体定义 d ·
         d 写明三个集共用的类与四条态射 ·
         d 不含任何具体条目 · d 与元工程既有的本体定义口径一致
```

分解是拿出一组任务单元 T = {t₁, …, tₙ}，再给出先后关系 ≺，要满足三条：终态蕴含目标、依赖保证前置、每个单元的判据可判定。

| 任务单元 | 执行者 | 前置 | 判据 |
|:--|:--|:--|:--|
| 定本体边界 | human | 无 | 人拍板：写出哪些进本体（类、态射、对象属性）、哪些判为实例不留，两项都写死 |
| 抽共性与差异 | agent | 定本体边界 | rule：对照表落盘，含三集的类名一栏与四条态射签名一栏；agent：通读一遍，差异是不是只在类名 |
| 对齐元工程口径 | human | 抽共性与差异 | 人拍板：本体的组成（存在什么、彼此什么关系、必须成立什么）与元工程已写的本体定义对得上 |
| 落本体文件 | agent | 对齐元工程口径 | rule：文件落盘且含三类对象与四条态射；agent：通读一遍，像不像一份本体定义 |
| 核可搬运 | agent | 落本体文件 | rule：扫一遍全文，不出现任何具体条目名；agent：判有没有把实例当成骨架写进来 |

先后关系画出来是这样：

```text
定本体边界 ─→ 抽共性与差异 ─→ 对齐元工程口径 ─→ 落本体文件 ─→ 核可搬运
```

对着三条逐条看。

终态蕴含目标：全部走完，元工程仓里有一份本体定义，写明了三类对象与四条态射、不含具体条目、口径与既有定义一致，G 成立。

依赖保证前置：抽共性与差异要求边界已定，正好是「定本体边界」的后置；对齐口径要求对照表已在，正好是「抽共性与差异」的后置；落文件要求口径已对，正好是「对齐元工程口径」的后置；核可搬运要求文件已在，正好是「落本体文件」的后置。没有一步等着一个还没做的前置。

判据可判定：两条人拍板（边界、口径）由人给出是或否；三条 `rule` 判据由程序核对（文件在不在、含不含四条态射名、有没有出现条目名）；两条 `agent` 判据要读一遍才判得出，是或不是边看边说。没有一条落空。

三样里最容易漏的是第二条。人排步骤习惯按「先定、再抽、再写、最后核」顺着写，看着顺，但落到具体判据上容易漏掉一条依赖：核可搬运要扫的是**落下来的文件**，它等的是「落本体文件」，不是「对齐口径」——中间少一条边，就会出现文件还没写、人已经在核搬运的情况。

## 代码实现

上面五个任务单元，在本领域的格式里落成一份工作流定义：

```yaml
name: 认知地图本体移交元工程
description: 把三个记忆集共用的认知地图本体（类与态射）提炼出来，落到元工程仓
steps:
- name: 定本体边界
  description: 写清哪些进本体（类、态射、对象属性）、哪些判为实例不留
  executor: human
  criteria:
  - executor: human
    description: 两类清单都已写死，不留待定项
- name: 抽共性与差异
  description: 对照三份 index.ttl，抽共有的类与四条态射，列出只在命名与类名上的差异
  executor: agent
  criteria:
  - executor: rule
    description: 对照表落盘
    path: artifacts/本体对照表.md
  - executor: rule
    description: 四条态射名齐
    file: artifacts/本体对照表.md
    contains: evokes
  - executor: agent
    description: 通读一遍，确认差异只在类名与命名空间
- name: 对齐元工程口径
  description: 与元工程已写的本体定义（存在什么、彼此什么关系、必须成立什么）逐条对齐
  executor: human
  criteria:
  - executor: human
    description: 口径已拍板，不一致处已写明取舍
- name: 落本体文件
  description: 把本体写成独立文件，落在元工程仓的本体目录
  executor: agent
  criteria:
  - executor: rule
    description: 文件落盘
    path: artifacts/认知地图本体.md
  - executor: agent
    description: 通读一遍，像不像一份本体定义
- name: 核可搬运
  description: 扫一遍落下来的文件，确认里面没有具体条目
  executor: agent
  criteria:
  - executor: rule
    description: 不出现条目名
    file: artifacts/认知地图本体.md
    absent: 睡醒时的千头万绪
  - executor: agent
    description: 判有没有把实例当成骨架写进正文
```

字段与四样一一对上：`name` 是名字，`executor` 是执行者，`criteria` 里每条判据写着谁判、怎么算完，`steps` 的排列顺序就是选定的那条拓扑序。前置和后置没有自己的字段，写在 `description` 里——这一段留给人和智能体读，程序核不了。

这段定义能做机械核对的部分，本领域的工具箱已经实现：读它的是工作流定义的入口（`Workflow::from_value`）。它管的是字段合法性——步骤名不能空，`executor` 只能是 `agent` 或 `human`，判据只能取 `rule` / `agent` / `human` 三种、判法只能是 `path` / `absent` / `contains` / `run` 四种，出现不认识的字段当场报错。判据为空它不拦。

三条分解条件里，程序替人看住的是取值的合法性；终态蕴含目标、依赖保证前置这两条没有对应字段，只能由拆的人拿着产物逐条读。这里还有一处只有人核得住：**「不含具体条目」这条判据**，程序只能拿一个已知的条目名去试（上面那条 `absent` 就是拿一个名字当探针），它证不了「一个都没有」——真正的核还是得读一遍。哪些条件程序管得住、哪些只能人核，这段落点就在这里。
