# 交互设计：元认知档案（quanttide-design 域）

**意图（创始人原话，2026-11-01）**：「我发现『命名』实际上是最重要的分水岭，比如我刚才写媒体云的时候问到了『列表-详情』。我对各种交互范式很熟悉，但是不知道如何准确命名他们。」

**真身**：领域仓在（quanttide-design，交互设计定位），`data/journal`、`data/profile`、`data/intention` 子模块已注册未冷启动；`insight`、`roadmap`、`brochure` 三仓未建；`apps/qtcloud-design`、`packages/quanttide-design-toolkit`、`examples/quanttide-design-lab` 在。命名表从零开始——第一条素材是媒体云设计里遇到的「列表-详情」。

## 核心循环

**设计中遇到布局/流程选择 → 描述对名 → 你确认采纳 → 落命名表 → 下次直接叫名字复用。**一等对象是交互范式；你脑子里有范式，缺的是名字——命名表就是把「熟悉但叫不出名」的东西接上通行词汇。

## 已落死的判据（岔路问答，2026-11-01）

1. **名字从社区通行词汇对齐取用**：英文原名＋中文对照，找到了就用，不发明；只有社区确实没有对应词、或刻意做词义位移时才自造，自造名归创始人定。叫 master-detail，AI 和组件库都听得懂；叫自造名，一切从头解释；
2. **只从真实设计实践收录，不铺市场清单**：市场上的范式清单很多、帮助不大——表要对得上量潮自己在用的东西；遇到才认，认了才收；
3. **条目带实践的适用条件与实例**：不收光秃秃的市场定义——每条写明量潮在哪次设计里用了它、什么情况下选它。

## 待定判据（岔路问答未做，不得先填）

1. **范式的切分粒度**：列表-详情＋分页＋筛选算几条，待真实条目攒起来后定；
2. **认名环节的确认方式**：AI 对名后你怎么采纳（一句话确认还是有别的动作），跑几次实际认名后定。

## 两段分工与落位

第一段（遇到 → 命名事件落档）落 `journal` 范畴，只增不改，细节见 `journal.md`；第二段（命名事件 → 命名表条目）落 `profile` 范畴，快照替换，细节见 `profile.md`；要到哪去落 `intention`，对外口径落 `brochure`；`insight`、`roadmap`、`brochure` 三仓未建，稿件已备在 staging，建仓后注入。子系统不自建容器。

## 任务单元

| 任务 | 执行者 | 判据 |
|:--|:--|:--|
| 定范式、命名事件的判定 | human | 给定一段设计记录，判得出这算不算一次命名事件 |
| 认名对名 | agent | 遇到的范式对上社区通行名，给英文原名＋中文对照＋出处 |
| 采纳落表 | human | 名字归用户——对上的名由创始人确认才落表 |
| 核回溯 | agent | 每条表目指得到它第一次出现的应用与页面 |

## 已有资产（别重复建设）

- 领域仓 README 已定位「整合各应用的交互设计经验成统一语言」——命名表就是这句话的落地形态，不另起概念；
- `packages/quanttide-design-toolkit` 是命名表将来可去的地方（标准库），命名表先在 `data/profile` 长，成熟了再进 toolkit。

## 边界

- 收录的是范式命名，不是设计评论——名字对不对得上是一回事，设计好不好是另一回事（后者归 product 或当场沟通）；
- 范畴不补领域判断：切分粒度、确认方式必须人给。
